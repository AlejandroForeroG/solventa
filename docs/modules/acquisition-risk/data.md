# Acquisition and risk data

`quotes` stores the canonical request and idempotency key per partner/subject. Reusing a key with a different `request_hash` must be rejected in application: UNIQUE only prevents another row. JSON must contain minimal canonical data, without plaintext PII, secrets or unfiltered external responses. DDL does not inspect JSON; validate and tokenize in adapters.

The minimum-data quote writes the `quotes` row, its audit event and the `quote.created` outbox event in one transaction. Exactly one of `partner_id` and `client_id` is set (`quotes_one_actor`): a partner quote uses `partner_id` and, as `subject_token`, an HMAC of the customer's document; a web quote uses the user's `client_id` and `subjectToken`. `request_hash` is an HMAC keyed with `QUOTE_HMAC_KEY`; the document number, name and birth date are never stored. `normalized_request` holds the `decision-capture.v1` instance and `result` the response. The unique indexes `quotes_partner_idempotency` `(partner_id, idempotency_key)` and `quotes_user_idempotency` `(client_id, idempotency_key)` resolve a repetition in one statement, and the adapter compares `request_hash` to tell a repetition from a conflict, also when the same key arrives with another customer. `quote_code` (`COT-YYYY-NNNNN`) comes from `quote_counters`, incremented outside the quote transaction so it does not lock other quotes; a later failure leaves a gap, never a repeated code. Quote audit is retained five years, a provisional value.

Profiles preserve source, validity and consent per revision. Migration `0011_risk_profile_consent_reference.sql` adds the opaque public `CNS-*` reference while retaining legacy internal UUID references; exactly one representation is present per profile. Successful signal reads append a profile valid for at most two minutes and never beyond consent expiry. Decisions preserve rules, contract and `input_snapshot` for historical reconstruction. Runtime can only read/insert profiles and decisions, preserving that history. `offer_revisions` holds immutable terms per `(offer_id, version)`, referenced by the policy. Commit each change to `offers`, its historical revision, audit and outbox in one local transaction. `offers` is the current projection; never reconstruct an earlier offer from that mutable row. Runtime cannot update/delete `offer_revisions`. Offers distinguish `preliminary` and `definitive`; application and SQL both prevent issuance from a preliminary offer.

See [permissions, events and SQL operations](../../infrastructure/data-model.md).

## Definitive offers and acceptance

Migration `0009_financial_offers.sql` adds append-only `offer_contexts` and `offer_acceptances`. Contexts bind an immutable terms snapshot and HMAC seal to the authenticated client/subject, source reference and actor-scoped creation key. Mortgage offers reference their owned quote and verified consent/version. A flight offer has its own opaque flight reference and no mortgage quote; underwriting decisions therefore allow a null quote reference for that independent product. No table references Identity or Policy SQL.

Migration `0010_offer_request_outcomes.sql` adds the append-only `offer_requests` ledger. Its primary key is `(client_id, idempotency_key)` and it binds the authenticated subject, canonical `[product, sourceReference]` request identity, first accepted/declined outcome and decision reference. Accepted outcomes also reference their offer. Creation commits this ledger entry, underwriting capture, current offer, immutable revision, sealed context, audit and `offer.created` outbox together. A declined mortgage decision commits the same ledger key with its actual capture, audit and `underwriting.declined` outbox without an offer. A same-key retry returns the committed outcome without reading changed provider data; another product/source conflicts. Concurrent accepted and declined attempts compete on the same unique key, and the losing transaction rolls back all its candidate business effects. Pre-ledger accepted offers retain compatibility through their original `offer_contexts` key and sealed owner/source checks; no historical backfill or financial decision re-evaluation occurs.

Captures retain the normalized score/debt ratio, applied base rate/version and adjustment so the academic premium can be reconstructed. Sources record capture time, live/stored/default quality, degradation flag, normalized failure, substitute and confidence. No raw provider body, name, document, birth date or token is persisted here. A degraded decision is stored as a preliminary offer and remains readable/replayable, but cannot be accepted.

Acceptance requires current authorization for the same consent/version used by a mortgage offer, including on recovery with the same key. A new grant does not authorize reuse of an old consent's inputs. Flight offers use no Open Finance data. The application verifies the terms seal and expiry; the SQL transaction also locks the owning current offer and checks its definitive state, offer expiry and authorization expiry against database time. The acceptance row, success audit and signed `offer.accepted` event commit together. Unique keys enforce one acceptance per offer and actor-scoped idempotency; a changed offer under a used key conflicts. After uncertain responses, recover with the same key and unchanged command.

`offer_contexts`, `offer_acceptances`, `offer_requests` and `offer_revisions` permit runtime SELECT/INSERT only. The mutable projection never replaces sealed historical terms. Reads validate the sealed owner as well as the lookup columns. A failed GET integrity check persists `offer.read` / `integrity_invalid` with the original request trace before returning 409; unavailable audit persistence returns 503 without exposing an offer. There is no synchronous call to Policy and no cross-owner transaction. The acceptance response means pending issuance; it establishes neither a charge nor an issued policy.

The Acquisition publisher selects only `offer.accepted`, claims at most ten records with a 120-second lease, preserves event IDs and verifies the complete allowed envelope plus HMAC before sending to its Queue binding. Each send has a five-second attempt deadline; success and failure updates require the current, unexpired lease. A late acknowledgment cannot mark a timed-out attempt published. The underlying Queue write cannot be cancelled; the Worker retains its lifetime with `waitUntil`, and recovery can redeliver the same event ID. It marks published only after timely acknowledgment. Failed sends defer for one minute, with at most five claims; malformed records and exhausted/interrupted final leases become `dead_letter`. Those records require operator inspection/reconciliation. A crash after send and before marking published can also redeliver: Policy must commit its inbox and financial effect before ACK. This is at-least-once delivery, not exactly-once transport.

Run `tests/offers.test.ts` for rules, authorization, missing sources, integrity and the shared Policy signature representation. `infra/offers-smoke.mts` exercises real local owner transactions, concurrent accepted/declined retries, traced GET integrity rejection, failure rollback, publisher leases/retries/quarantine and immutable runtime grants. Its Identity check and external providers are explicit stand-ins; passing it does not establish remote delivery, native behavior, actuarial validity or real financial-provider integration. Remote migrations, environment-specific secrets/queues and deployed flows require their own verification.
