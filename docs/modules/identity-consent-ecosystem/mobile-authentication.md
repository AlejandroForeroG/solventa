# Native authentication

Native clients authenticate with WorkOS AuthKit using authorization code + PKCE, store their tokens on the device and send the **user access token** as `Authorization: Bearer <token>` to Solventa's public gateway. Identity owns verification, local registration, permission decisions and revocation. The gateway forwards to its private Identity binding with the existing five-second API deadline and version gate. See the [OpenAPI contract](../../../packages/contracts/openapi/v1/mobile-authentication.yaml), [mobile integration guide](../../channels/mobile/README.md#connecting-native-login) and [Bruno requests](../../../tools/bruno/solventa/README.md).

## Routes

All paths below include `/api/v1`. Responses have a correlation UUID in `X-Trace-Id` and `traceId`, `Cache-Control: no-store` and `X-Content-Type-Options: nosniff`.

| Route | Method | Behavior |
|---|---|---|
| `/mobile/config` | GET | Public client ID, fixed callback `solventa://auth/callback`, WorkOS authorization/token endpoints |
| `/mobile/session` | POST | Verify the user token and register the local client/session; active retries return the same principal |
| `/mobile/session` | GET | Verify the user token and inspect the existing active local session |
| `/mobile/session` | DELETE | Revoke locally, then at WorkOS; return `status: signed_out` after both steps |
| `/access/mobile` | GET | Verify the token and active local session, then return the native user actor for `quotes:create` |
| `/mobile/devices/{installationId}` | POST | Register one installation bound to the verified active provider session, within ten minutes of local session creation |
| `/mobile/devices/{installationId}` | GET | Check the session-owned installation binding is active; never register or extend it |
| `/mobile/devices/{installationId}` | DELETE | Revoke binding and its local session with audit/outbox, then revoke the provider session |

POST and DELETE need no body. Identity derives the principal from verified claims; a supplied client ID has no effect. Protected native routes reject any Cookie header with 400. They never interpret sealed web cookies, partner M2M tokens, server API keys or `subjectToken` as native credentials. Unsupported methods return 405 with Allow. Missing, malformed, foreign or expired tokens and unavailable local sessions return 401 with a Bearer challenge. Missing configuration or unavailable dependencies return 503; permission policy denials return 403.

## Verification and persistence

The outbound adapter uses the environment's WorkOS client-specific JWKS, RS256, exact issuer `https://api.workos.com/user_management/<clientId>`, matching `client_id`, user `sub`, session `sid` and valid integer `iat`/`exp`. An audience, when present, must match the client. Impersonation tokens are denied. Provider `getUser` checks that the current user exists and has a verified email. Only provider public keys are cached; account/session authorization is never cached. WorkOS calls have explicit timeouts and no SDK retries.

Registration reuses the [existing identity store](authentication.md). Client, provider mapping, session, audit and first-client outbox commit in the owner's transaction. Active registration retries do not duplicate audit/outbox or extend expiry. Conflicting first registrations resolve through the unique mapping and one bounded lookup/retry; a serialization rejection retries only after confirmed rollback, never after an uncertain commit. Expired or revoked session references cannot be reopened; a suspended client cannot register. Maximum local session duration remains seven days. GET and access checks never register, refresh or extend a session. No schema changes are required.

Every use requires a current signed token and active local session belonging to that provider user. The access actor has `kind: user`, `channel: mobile`, a pseudonymous principal and `operations: [quotes:create]`. This is a permission probe, not a native quote endpoint. The private authorization RPC also accepts `{kind:'mobile', token, operation:'quotes:create'}`; native consent operations are denied. Existing quote/consent HTTP adapters retain their own channel contracts and must be extended deliberately before native business calls.

Logout revokes an existing local session or creates an already-revoked blocking reference in one owner transaction, including any new client/provider mapping, outbox and revocation audit. It never commits an active session during logout. A SQL failure rolls back the complete operation and stops provider revocation; it returns 503 and must not be reported as completed logout. A concurrent first bootstrap cannot reopen a successfully committed blocking reference. Confirmed serialization/uniqueness rollback permits one bounded retry; an uncertain commit is never retried automatically. If WorkOS revocation fails after SQL commits, HTTP returns 503 while the local session remains unusable; a bounded retry with a still-valid access token can finish provider revocation. An already missing provider session is a safe retry. Offline device logout cannot revoke remotely until connectivity returns; do not report server revocation from a local token deletion. External WorkOS revocation is reflected on access-token expiry/refresh: no revocation-event consumer or per-request session introspection exists. `getUser` verifies account state, not provider session state.

## WorkOS configuration

Reuse the environment's existing `WORKOS_API_KEY` and `WORKOS_CLIENT_ID` in Identity; no new server secret goes to the app. Each local/dev/staging/prod WorkOS environment must register the exact additional Redirect URI `solventa://auth/callback`, preserving its web callback. Enable public native authentication with PKCE according to [WorkOS's Expo example](https://github.com/workos/expo-authkit-example). Mobile never needs `WORKOS_API_KEY`, `AUTH_COOKIE_PASSWORD`, consent sealing keys, the infrastructure token or a partner secret. Keep the existing provider and branding choices.

GET `/mobile/config` reports the backend's public configuration; it does not establish that the callback is registered at WorkOS. Operators must separately verify the allowed redirect and a browser login/code exchange. Do not substitute one environment's client/token for another's. The [channel guide](../../channels/mobile/README.md) lists the public bases and implementation steps.

## Validation and limits

`npm run test:authentication` covers JWT isolation, signature/time failures, verified/deleted users, local session policy, HTTP lifecycle and fail-closed provider errors. `npm run test:contracts` validates actual HTTP bodies/statuses against OpenAPI. `npm run test:authentication:sql` verifies real local registration, active replay, concurrency, suspension, expiry, atomic pending logout, complete rollback after a denied audit insert, bootstrap/logout races and revocation in a disposable database. Bruno provides reproducible native requests using a user token held only as a local secret variable.

### Installation bindings

Local web and native logout share the owner-scoped transactional device cascade. If a sealed web cookie and native token identify the same WorkOS session, either logout revokes the associated bindings with audit/outbox/capture in the session transaction. Replays do not duplicate effects; both paths also repair bindings left active on an already-revoked session. Failure to persist the cascade rolls back session and device changes and stops provider logout. Web logout retains its cookie/Origin checks and response body, and forwards its supplied or generated `X-Trace-Id` to the same audit/capture correlation.

The new device routes leave the closed `/mobile/config` response unchanged from contract 1.1.0. Existing configuration clients receive only the five original fields; they need no new feature flag or schema change. Verify device-route availability from the selected deployment's OpenAPI and successful deployment before running the installation examples.

The domain policy owns the ten-minute creation boundary, one installation per session and no reactivation. Application supplies that policy and historical capture to the store's transactional operation. SQL loads the owner-scoped session and binding snapshot under the session lock, evaluates the supplied operation while holding it and applies the resulting plan; alternate stores use the same core decision. The database observation time and session timestamps determine freshness. Existing active-binding replays remain valid after the creation window while the session remains active.

An authenticated active session denied for an expired registration window, a replacement installation or a revoked binding produces `device.registration_denied` audit and `identity.device_registration_denied` outbox in the same transaction. They share a generated decision UUID (`resource_type`/`aggregate_type` `device_registration`), request correlation and capture of the actual session/binding snapshot, evaluation time, window, rule version and internal reason. The public response remains opaque 401. Failure to commit the required denial record returns 503 and rolls back audit/outbox; no durable denial is claimed then. Invalid credentials, unknown/foreign sessions and read-only misses do not create registration decisions. Rows in outbox do not establish event publication or consumption.

The native consumer Pact is deferred until the mobile caller and its generation/comparison test are delivered together. Device HTTP behavior is checked against OpenAPI; provider-only replay is not evidence of mobile-client compatibility.

Version-2 capture inputs also use canonical lowercase installation IDs when the locked binding or its stored reference is legacy uppercase. Application normalizes binding snapshots and the shared web/native logout cascade normalizes extracted installation IDs; neither operation rewrites the legacy reference.

Explicit device-operation captures identify `session-bound-installation` rule version `3`, which retains canonical UUID identity and evaluates account activity in Domain for registration/read while allowing owner-scoped revocation for suspended clients. Its session snapshot includes `clientActive`. Version `2` retains its [immutable policy](https://github.com/AlejandroForeroG/solventa/blob/c849f86aa214500fd926994487e2e8c80c115c34/backend/identity-consent-ecosystem/src/domain/registered-device.ts) and [SQL snapshot filter](https://github.com/AlejandroForeroG/solventa/blob/c849f86aa214500fd926994487e2e8c80c115c34/backend/identity-consent-ecosystem/src/adapters/outbound/registered-devices.ts). Session logout cascades use the distinct `session-device-logout` rule version `1`: revoke all active bindings owned by the verified provider session, irrespective of account activity or session expiry/revocation; its inputs are action, canonical installation UUID and session binding. This path does not evaluate the registration/read account-activity rule. Existing `session-bound-installation` version `1` records are not rewritten or reinterpreted: its [immutable policy source](https://github.com/AlejandroForeroG/solventa/blob/9f7af0ab934447d18ba76238b41ea0ffdf424d2c/backend/identity-consent-ecosystem/src/domain/registered-device.ts) and [capture metadata source](https://github.com/AlejandroForeroG/solventa/blob/9f7af0ab934447d18ba76238b41ea0ffdf424d2c/backend/identity-consent-ecosystem/src/application/registered-devices.ts) remain available with the old textual comparison behavior. This is an internal rule version; API `v1`, OpenAPI `1.2.0` and capture schema version `1` remain unchanged.

Installation UUID equality ignores hexadecimal case. Application canonicalizes new inputs/references and response installation IDs to lowercase; Domain also matches legacy uppercase binding references without replacing them or changing their device ID. Registration replays, GET and DELETE accept either representation. Supplied UUID traces are likewise canonicalized to lowercase before they enter response headers/bodies, audit and decision captures, preserving one correlation value and the shared capture schema.

Contract 1.2.0 adds the device route compatibly. The installation ID is a random UUID v4, not an authentication credential. Every call verifies the user token and resolves its provider subject/session on the server. SQL binds `registered_devices.device_reference` to `mobile-v1:<provider-session>:<installation-uuid>`; no schema or runtime-grant change is needed. One installation per provider session prevents retargeting a session after registration. Active same-binding retries return the original ID without duplicate audit/outbox. Revoked bindings cannot reactivate; a new primary login/session is required. A fresh local registration window is not proof of fresh provider password entry or platform attestation.

Device creation and explicit revocation use a session-row lock and one owner transaction containing the binding, audit and outbox with historical decision capture. No automatic SQL write retry follows an uncertain commit. Logout revokes associated bindings and emits their audit/outbox in its existing session transaction. Its session audit, device audit, outbox and capture retain the initiating HTTP request's correlation UUID, including a server-generated UUID when the supplied header is invalid or absent. Device DELETE also revokes its local session, so bearer requests cannot continue using a still-signed token. Same-owner DELETE and retries remain possible for suspended clients and after local revocation if the provider step needs retrying; foreign/unknown bindings disclose no ownership and return 401. Reads require an active account/session and an unrevoked exact binding. No tokens, hardware identifiers or biometric templates enter SQL.

Backend authenticated HTTP verification is separate from native biometric validation. Native secure custody and platform validation remain separate channel responsibilities; see the [mobile guide](../../channels/mobile/README.md). The server does not attest a biometric prompt: only the native protected key enforces local credential release. A compromised/rooted client is outside this trust claim. This increment adds no consent onboarding, policy purchase or claims flow. A verified WorkOS session does not prove biometric identity or consent. Deployment of 1.2.0 and real SQL/device evidence are required before claiming the complete flow operational.
