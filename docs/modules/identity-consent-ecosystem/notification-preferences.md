# Notification preferences

Identity owns the authenticated customer's category and channel choices. The native route and versioned contract are in [notification-preferences.yaml](../../../packages/contracts/openapi/v1/notification-preferences.yaml); the response example is [notification-preferences.json](../../../packages/contracts/examples/notification-preferences.json). The mobile flow is described in the [mobile guide](../../channels/mobile/README.md).

`GET /api/v1/mobile/notification-preferences` returns all-disabled defaults at version zero until the first save. `PUT` replaces the complete matrix for policy, payments, claims and commercial notices over push, email and SMS. It requires `expectedVersion` and an `Idempotency-Key`. A stale version or a key reused with another payload returns 409. An identical retry returns the committed result. The caller reads again after a successful save to obtain current state if another session changed it meanwhile. Only the verified native customer can read or change their own choices; cookies and partner identities are rejected. Failed required denial recording returns 503.

Migration `0011_notification_preferences.sql` adds the owner record and idempotency command table. Apply it in each environment before deploying the Worker, using the [migration guide](../../infrastructure/migrations.md). A successful change commits the choice, command, audit and outbox in the Identity database transaction. The outbox event contains the matrix so a future delivery consumer can apply the choice version; this increment does not send messages. There is no cross-service atomicity or claim of provider delivery. The commercial category starts disabled. All categories start disabled until the customer explicitly chooses channels.

Push permission is device-local and is never inferred from the stored preference. A chosen push channel can be non-operational when the OS denies permission; the mobile screen tells the customer to enable it in Settings. Permission on another device does not change the account's stored choice. The delivery service must recheck the current choices and its device registration before sending; the stored matrix alone does not authorize delivery. Critical notices and in-app feed behavior belong to the separate delivery increment.

Run `npm run test:notification-preferences`, `npm run test:notification-preferences:sql`, `npm run check`, then validate the permission allow/deny and Settings return flows in a native development build. The SQL smoke requires the local Identity database and migration. The native permission check cannot be established by the web export.
