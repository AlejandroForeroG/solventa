# Policy lifecycle

The web policy portal supports owner-authorized modification, renewal and cancellation through `POST /api/v1/policies/{policyId}/lifecycle`. Identity verifies the existing web session, same-origin write and `policies:manage`; Policy derives both owner identifiers from that principal. Partner credentials, native tokens and arbitrary customer identifiers cannot authorize this operation. Advisor delegation is not implemented: an advisor must not act as another customer using this endpoint.

Modification and renewal link an independently issued replacement policy of the same product and owner. Its offer, premium confirmation and signature use the existing purchase flow. The source and replacement documents are checked and their hashes sealed into the change record. A replacement is usable once, cannot itself be ended and must not predate the source signature or start in the future. Modification requires an unexpired source. Renewal requires the source to have expired and the replacement validity to start no earlier than the source expiry. The portal explains eligibility before linking to a replacement purchase. This model does not amend or reprice a signed contract in place.

Cancellation uses `replacementPolicyId: null`. All three operations preserve the original issuance state, signed document and confirmed premium as historical evidence. They do not automatically refund, prorate or settle an external balance. The separate sealed lifecycle state ends the original coverage from the recorded change instant. New parametric occurrences at or after that instant are rejected; earlier occurrences and previously accepted payment recovery retain their existing behavior. Replacement coverage is evaluated through its own policy. A web detail or generated PDF shows the recorded change alongside the historical document and payment; the original canonical signed bytes are unchanged.

## Persistence and retries

Apply `0011_policy_lifecycle.sql` and its `SELECT, INSERT` runtime grants before publishing dependent code. `policy_lifecycle_changes` is append-only and has one change per source, one use per replacement, and an actor-scoped command identity with a request fingerprint. Commands lock owned source and replacement policies in deterministic order. An identical retry returns the committed state; a changed payload, an ended source or a reused replacement returns conflict. Missing resources and foreign resources remain opaque.

The lifecycle record, decision capture, audit and customer notice commit in the same owner transaction. A failed audit or outbox write rolls back the change. The capture retains the actual document fingerprints, offer and payment evidence, reason code, timestamp and `academic-policy-lifecycle-1` rule version. The audit retains its actor reference and correlation ID under the existing retention policy. No raw caller idempotency key or free-text personal reason is persisted.

The `policy.lifecycle.notice` v1 payload follows [policy-lifecycle-notice.v1.json](../../../packages/contracts/schemas/policy-lifecycle-notice.v1.json): owner pseudonym, source and replacement references, action, change ID/time and `refund: not_automated`. Its event ID is the change ID; an eventual consumer must deduplicate that identity before acknowledging. The separate `policy.policy.lifecycle.changed` event retains the full decision capture. Persistence prepares notification delivery; there is no delivery claim or new notification consumer in this feature.

## Channel projections and verification

The web issued list retains ended contracts with `contractStatus`; detail retains their sealed `lifecycle` history. The native wallet route excludes ended contracts in SQL before applying its six-policy limit, so a fresh sync replaces its protected snapshot without advertising ended coverage. An offline copy remains explicitly stale until the next successful sync; its existing device authentication and encrypted storage are unchanged.

The [v1 policy contract](../../../packages/contracts/openapi/v1/policies.yaml) defines the command and response; v2 reads also expose optional lifecycle evidence. Run `npm run test:financial`, `npm run test:web`, `npm run lint:openapi` and `npm run test:financial:sql`. The SQL suite uses a disposable database with actual migrations, owner grants, mock payment/signature protocols, atomic rollback checks and competing replacement commands. External settlement and notification delivery are outside those checks.
