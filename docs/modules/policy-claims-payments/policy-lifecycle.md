# Policy lifecycle

The web policy portal supports owner-authorized modification, renewal and cancellation through `POST /api/v1/policies/{policyId}/lifecycle`. Identity verifies the existing web session, same-origin write and `policies:manage`; Policy derives both owner identifiers from that principal. Partner credentials, native tokens and arbitrary customer identifiers cannot authorize this operation. Advisor actions use separate, explicitly approved routes described below; this owner route never impersonates a customer.

Modification and renewal link an independently issued replacement policy of the same product and owner. Its offer, premium confirmation and signature use the existing purchase flow. The source and replacement documents are checked and their hashes sealed into the change record. A replacement is usable once, cannot itself be ended and must not predate the source signature or start in the future. Modification requires an unexpired source. Renewal requires the source to have expired and the replacement validity to start no earlier than the source expiry. The portal explains eligibility before linking to a replacement purchase. This model does not amend or reprice a signed contract in place.

Cancellation uses `replacementPolicyId: null`. All three operations preserve the original issuance state, signed document and confirmed premium as historical evidence. They do not automatically refund, prorate or settle an external balance. The separate sealed lifecycle state ends the original coverage from the recorded change instant. New parametric occurrences at or after that instant are rejected; earlier occurrences and previously accepted payment recovery retain their existing behavior. Replacement coverage is evaluated through its own policy. A web detail or generated PDF shows the recorded change alongside the historical document and payment; the original canonical signed bytes are unchanged.

## Persistence and retries

Apply `0011_policy_lifecycle.sql` and its `SELECT, INSERT` runtime grants before publishing dependent code. `policy_lifecycle_changes` is append-only and has one change per source, one use per replacement, and an actor-scoped command identity with a request fingerprint. Commands lock owned source and replacement policies in deterministic order. An identical retry returns the committed state; a changed payload, an ended source or a reused replacement returns conflict. Missing resources and foreign resources remain opaque.

The lifecycle record, decision capture, audit and customer notice commit in the same owner transaction. A failed audit or outbox write rolls back the change. The capture retains the actual document fingerprints, offer and payment evidence, reason code, timestamp and `academic-policy-lifecycle-1` rule version. The audit retains its actor reference and correlation ID under the existing retention policy. No raw caller idempotency key or free-text personal reason is persisted.

The `policy.lifecycle.notice` v1 payload follows [policy-lifecycle-notice.v1.json](../../../packages/contracts/schemas/policy-lifecycle-notice.v1.json): owner pseudonym, source and replacement references, action, change ID/time and `refund: not_automated`. Its event ID is the change ID; an eventual consumer must deduplicate that identity before acknowledging. The separate `policy.policy.lifecycle.changed` event retains the full decision capture. Persistence prepares notification delivery; there is no delivery claim or new notification consumer in this feature.

## Channel projections and verification

The web issued list retains ended contracts with `contractStatus`; detail retains their sealed `lifecycle` history. The native wallet route excludes ended contracts in SQL before applying its six-policy limit, so a fresh sync replaces its protected snapshot without advertising ended coverage. An offline copy remains explicitly stale until the next successful sync; its existing device authentication and encrypted storage are unchanged.

The [v1 policy contract](../../../packages/contracts/openapi/v1/policies.yaml) defines the command and response; v2 reads also expose optional lifecycle evidence. Run `npm run test:financial`, `npm run test:web`, `npm run lint:openapi` and `npm run test:financial:sql`. The SQL suite uses a disposable database with actual migrations, owner grants, mock payment/signature protocols, atomic rollback checks and competing replacement commands. External settlement and notification delivery are outside those checks.

Missing and foreign source/replacement policies keep the same opaque 404 after Identity durably records the minimal `policies:manage` resource denial. If that required security audit cannot be committed, the route returns 503 `access_unavailable` instead. No policy, replacement or actor identifier enters the denial RPC.

## Explicit advisor authorization

The owner opens an issued policy in `/polizas` and grants one exact action to the advisor's opaque professional reference. The approval binds the owner/advisor identifier tuples, source document, action, an independently issued replacement and its document hash when applicable, and a future expiry of at most seven days. Its reference is a selector, never a bearer credential. The owner can page through and revoke every approval, including older active approvals; no customer identifier is accepted in the request body. Both document fingerprints and every original lifecycle rule are checked again at execution. The advisor cannot quote, accept, pay, consent or sign on behalf of the customer through these routes.

The separately authenticated advisor opens `/asesor`. Identity requires a current administrative `policy_advisor_grants` record, active client, exact WorkOS session and a `policies:manage-delegated` lease bounded by session/grant expiry and five seconds. Mobile and M2M are excluded. Pages contain at most twenty approvals addressed to that principal and current professional reference, without the owner's portfolio, personal identity, signed bytes or payment details. The customer must obtain this reference from the intended advisor; the application exposes no customer/advisor directory.

The [advisor contract](../../../packages/contracts/openapi/v1/advisor-authorizations.yaml) defines owner grant/list/revoke and advisor list/execute. Grant creation uses a single Identity RPC to authenticate the owner and verify target eligibility; Policy verifies ownership and records the customer's actual approval. Execution uses one fresh Identity authorization, then resolves the owner/action locally from the sealed approval. Administrative eligibility never substitutes for customer approval. All writes enforce the existing sealed-cookie and Origin policy. Missing, foreign, expired and revoked approvals remain opaque.

Apply Policy `0012_advisor_authorizations.sql` and Identity `0015_policy_advisors.sql` through the environment-bound migration job before publishing. Policy grants/revocations/executions are append-only at runtime. Execution and revocation share the source policy lock; source and replacement locks retain deterministic order. SQL checks customer expiry and professional lease using the current database clock. Application checks both again after write and replay. Any failed execution/audit/capture/notice insert rolls back the entire change. A revoked approval never permits a protected replay. An executed action remains historical when its approval is subsequently revoked; revocation does not undo it.

The existing lifecycle v1 seal and owner-addressed notice remain unchanged. `advisor_lifecycle_executions` links the change to approval, owner and advisor executor; the decision capture retains the delegated context and both document bindings. Audit attributes the lifecycle change to the authenticated advisor, while the notice always targets the owner. No external provider is called by delegated lifecycle execution. Grant and revocation retain their own `policy-advisor-authorization-1` decisions. Caller keys are hashed and scoped to the executor; altered payloads conflict.

### Professional eligibility administration

An authorized SQL administrator uses `node infra/policy-advisor-access.mjs <environment> grant <private-file>` or `revoke`. Grant files contain exactly `grantId`, `clientId`, `expiresAt`, `operatorReference`; revocations contain `grantId`, `operatorReference`. UUIDs are canonicalized; grant expiry is future canonical UTC and at most ninety days. The command validates an active client and commits the eligibility change and audit together. Runtime has SELECT only and cannot self-enroll. Revoke an expired unrevoked grant before replacing it; a new reference does not inherit approvals to the old one.

Run `npm run test:financial`, `npm run test:financial:sql`, `npm run test:web` and the advisor consumer/provider Pact tests. SQL checks exercise actual runtime permissions, distinct owner/executor, idempotent execution, revocation and atomic rollback. Unit tests cover expiry during write/replay, altered seals/references, owner isolation and fail-closed audit; these synthetic identity boundaries do not replace the authenticated browser journey.

Approval lists use a keyset `after` cursor returned as `nextCursor`, ordered by grant time and UUID descending. Both owner and advisor pages retain their exact principal scope; changing a cursor never changes the subject. The web provides previous/next navigation so older active permissions remain revocable.
