# Policy, Claims & Payments

Code: `backend/policy-claims-payments`. This module owns issuance, policies, premiums, payments, reconciliation, claims, evidence and indemnities. It receives Acquisition offer references; it maintains separate adapters for payments, signatures and other integrations it owns.

## Implemented state

The Worker owns its `policy` schema, runtime role and Hyperdrive. Its academic financial flow consumes signed accepted-offer events, persists policies and charges, signs and issues them using explicit mock provider adapters. The internal event consumer evaluates verified flight-delay events against the immutable coverage and creates a single indemnity/payment effect. Business rules, SQL transactions, authorization, integrity verification and idempotency execute in Solventa; only external data, payment and signature providers are mocked. This does not establish legal issuance, real money movement, PCI compliance, external provider integration or production readiness. Evidence upload, assisted claims and lifecycle changes remain separate capabilities.

## Financial HTTP flow

All routes below enter through the web Worker and require the existing sealed web session. Identity verifies the operation, local session and Origin for each write through one `authorizeFinancialAccessV1` RPC. Partner bearer tokens and native credentials do not authorize these web financial operations. Unknown fields are rejected without echo; errors contain only `error` and `traceId`. Responses include `Cache-Control: no-store`, `X-Trace-Id` and `X-Content-Type-Options: nosniff`. API version retirement headers remain applied by the gateway.

1. Accept an immutable definitive offer in [Acquisition](../acquisition-risk/README.md#definitive-synthetic-offers). Its 202 response means `pending_issuance`, not a confirmed charge or policy.
2. Read `GET /api/v1/policies/by-acceptance/{acceptanceId}/policy` until the owner's signed outbox event has been consumed. A missing, pending or foreign acceptance returns the same opaque 404. Before import, an absent row is an internal pending result and does not create a financial rejection or security-denial alert on each poll. An existing foreign policy still follows the audited denial path. Authentication/authorization always precedes this lookup. The query never creates a policy and returns the full document once available.
3. Read `GET /api/v1/policies/{policyId}` to review/download the returned `document` and its opaque HMAC-SHA256 `documentHash`. Return this server-provided fingerprint unchanged; clients never receive the signing key.
4. Confirm `POST /api/v1/policies/{policyId}/issue` with JSON `{ "documentHash": "<reviewed 64-character lowercase fingerprint>" }` and an `Idempotency-Key` of 1–128 visible ASCII characters. The JSON limit is 1024 bytes. Clients cannot submit the amount, destination, owner, approval or alternative offer terms.

Issuance derives money and ownership from the stored, integrity-checked acceptance. It orders premium charge, document signature and issuance through durable owner states with stable mock provider keys. A failed signature compensates a confirmed mock charge. An uncertain result returns 503 and must be reconciled using the same operation identity; never invent a fresh key to repeat an uncertain charge. Different payloads under an existing key conflict. The returned policy identifies `synthetic: true` and `providerMode: mock`.

The [policy OpenAPI](../../../packages/contracts/openapi/v1/policies.yaml) is the public contract. Queue payloads follow [financial-event.v1](../../../packages/contracts/schemas/financial-event.v1.json); schema validation alone never authenticates an event. Consumers verify its HMAC, exact fields, environment, product/coverage, timestamps and immutable terms, persist effect/inbox/audit/outbox in their owner transaction, then acknowledge delivery. Delivery is at least once, not a distributed transaction or exactly-once transport. Rejected altered events must not create a financial effect. Parametric events have no public HTTP route.

## Academic rules and document integrity

The following numerical choices are academic implementation rules, not values prescribed by the functional or architecture sources. `academic-financial-1` preserves the flow/integrity rules. Acquisition versions its offer rules separately: a 15-minute offer/signature window, one-year mortgage coverage for the offered outstanding balance, and a separate one-day flight product with a 180-minute threshold and COP `100000.0000` indemnity, once per policy. A flight event does not trigger a mortgage indemnity. Money uses canonical DECIMAL(19,4) strings with four places and exact integer validation, never floating-point arithmetic.

The approved, signed offer revision supplies the premium, currency, coverage and validity. A producer's accepted event cannot be replaced by a provisional quote or a caller-supplied approval flag. Policy verifies the event's exact shape, HMAC and environment before import. An acceptance made after expiry is rejected. Delivery after a valid acceptance does not rewrite its history. A new premium is not started after the signing deadline; a prior confirmed premium is reconciled and refunded if the signature window has expired.

Documents are canonical JSON strings so SQL JSON property ordering cannot change their keyed fingerprints. On each protected use, the store's mutable policy projection must match the sealed terms, coverage and document. An issued policy additionally requires its persisted confirmed premium, valid synthetic signature receipt and keyed issuance timestamp in the append-only signature row. A parametric occurrence before that timestamp is not covered even if the offer's effective period already started; an administrator changing the timestamp without its keyed seal also blocks use. The timestamp records the owner's emission transaction, not an external legal timestamp. A command result cannot override those authoritative fields. The idempotency key is hashed with the actor before storage; raw caller keys are not copied into the financial command table.

## Transactions and recovery

Policy/premium states must agree before an operation: pending permits no premium or a pending/declined premium; charged/refunding requires confirmed; refunded requires refunded; issued requires confirmed and the sealed signature. Confirmed/refunded references must match the deterministic mock operation identity. An unknown provider lookup can start a settlement only for a pending intent. A claimed local confirmation without matching provider proof, or an altered confirmation reference, is audited and rejected without a new charge. These checks also preserve an uncertain pending operation's legitimate lookup-based recovery.

Recovery of HTTP issuance currently requires a client retry with its existing command identity; there is no autonomous issuance reconciler. Business outbox persistence does not deliver a customer notification. These remain explicit implementation limits.

The web channel implements those retries and reads the owned policy after a signature failure. The `signature_failed` code can also occur while another request is refunding; only an authoritative `refunded` state confirms compensation. The client preserves the original policy/document command key during recovery and does not claim a completed refund or offer another purchase while the state is `refunding`. A document mismatch requires another document read and explicit review before retrying confirmation. The existing charge/signature contracts remain owned by this module.

The final issuance transaction checks its timestamp strictly before the sealed offer deadline after acquiring the policy lock. Expiry while waiting for that lock atomically records a refund intent instead of a signature or issuance, then refunds outside SQL. Stored issuance timestamps at or beyond that deadline fail integrity checks, even with a matching timestamp seal. Refund orchestration rereads the current confirmed premium under lock and uses that confirmed provider reference rather than the earlier pending payment snapshot.

The additive financial migrations preserve the baseline tables. `financial_contracts`, `financial_payment_intents` and `policy_signatures` are append-only for runtime; `financial_commands` holds actor-scoped request fingerprints/results. The immutable payment intent records the provider idempotency identity, operation, key and HMAC. Mutable payment lookup starts from this reference rather than filtering mutable operation/key fields; tampering cannot hide an earlier payment and create another charge. Its foreign key also prevents changing the referenced payment ID. The HMAC binds the ID/key/operation as well as policy/amount/currency. A unique accepted offer/revision index prevents another policy even if a producer publishes a different acceptance ID. Inbox rows carry payload digests and policy references, so an identifier reused with changed content is a rejection rather than a replay.

No SQL transaction remains open during a provider call. The use case commits a stable payment intent, queries for a previous provider outcome, settles only when eligible and persists acknowledgement. `SqlMockPaymentGateway` keeps the explicitly synthetic provider's operations in `policy.mock_gateway_operations`; recovery therefore works across service instances and process restarts. Its ledger is separate from business state and does not establish distributed atomicity. A confirmed premium survives an emission persistence failure; a retry reconciles it without charging again. Signature failure or expiry first commits the `refunding` intent, which prevents concurrent issuance, then performs the idempotent provider refund. A concurrent operation that already issued wins before the refund intent, so its charge is not reversed. An uncertain acknowledgement/refund returns 503 and is recovered using the existing intent.

The owner confirms each business result with its audit/outbox, and each local consumer effect with inbox/audit/outbox. This includes `premium.requested` in the very first payment-intent transaction before any provider call, and `premium.declined` together with a rejected provider outcome. An outbox failure rolls back those writes rather than leaving an unaudited pending or declined payment. The SQL adapter combines related writes into data-modifying CTEs: policy/contract, payment/immutable intent, audit/outbox and payment/indemnity/claim confirmation. These reduce database round trips without changing transaction boundaries, grants, constraints or the required records. Payment discovery still rejects a missing intent with an orphan payment and validates every returned intent/payment binding. Provider calls remain outside SQL transactions.

Serialization and uniqueness conflicts retry only SQL work, at most three attempts; unknown commit outcomes are not blindly retried. The Queue handler acknowledges success or a durably recorded rejection and retries technical failures with bounded delay, ultimately retaining exhausted messages in the configured DLQ. Local/dev/staging consumers configure zero maximum batching wait, one message per batch and five retries with a dedicated DLQ; production has no financial consumer. A one-message batch avoids waiting for filling or for earlier messages' processing in the same invocation. It does not guarantee scheduler, processing or end-to-end audit latency. `financial_queue_delivery` logs only environment, generated/validated correlation UUID, attempt count, outcome, processing duration, event age and Queue-enqueue age at handler entry. Processing uses a monotonic duration; age measurements compare producer/consumer or Queue/consumer wall clocks and are diagnostic, not transport guarantees. Payloads, documents, cookies, credentials and provider references are not logged. Dev/staging `fetch` handlers use the database-region placement hint; it does not apply to Queue or RPC handlers. Configuration, code and local tests do not establish remote provisioning, delivery or a latency target. Stored business outbox entries do not establish customer notification delivery.

Rejections retain a fixed cause, generated decision UUID and trace UUID, without submitted bodies, cookies, signatures or personal fields. Required rejection persistence failure returns 503. Financial audit retention is provisionally 90 days; metadata does not implement deletion or protect against an administrator.

## Configuration and verification

`financial_http_duration` records only environment, the validated response correlation UUID, HTTP status, monotonic handler duration and a syntactically valid `cf-placement` diagnostic when provided by the platform. It does not log a URL, policy identifier, actor, cookie, request/response body or document. Correlate those durations with the Queue delivery metrics and client timing to distinguish processing from waiting; logs do not substitute the durable business audit.

Each new financial decision stores the application-generated [historical capture](data.md#financial-decision-history) atomically with its state/audit/outbox. It preserves the safe immutable offer/document context, original payment amount and identity, actual provider observations and covered occurrence rather than a generic resource-only placeholder. Completed replays preserve their original history; older captures are not backfilled. Persisted SQL checks cover the shared schema and exact business evidence, including refund/recovery and changes to live projections.

`FINANCIAL_PROVIDER_MODE=mock` explicitly enables synthetic providers only in local, dev and staging. An absent mode, missing/malformed `FINANCIAL_EVENT_KEY` (exactly 64 lowercase hexadecimal characters) or `APP_ENV=prod` fails closed. Keep the key in each environment's authorized secret custody; never copy it into clients or examples. Acquisition and Policy use the matching key for that environment, never another environment's credential. Apply the owner's additive financial migration and grants before deploying code that uses its tables, following [migration operations](../../infrastructure/migrations.md). Configuring Queue resources and secrets requires a separate verified environment operation; code and dry-run builds do not provision them.

`npm run test:financial` covers domain boundaries, event authentication, authorization and HTTP contracts. `npm run test:financial:sql` executes actual owner SQL and runtime grants in a temporary synthetic database: fresh migrations/replay, ownership, idempotency/concurrency, document binding, altered events, durable mock provider restart, uncertain confirmation reconciliation, recovery after an emission rollback, signature failure/expiry refunds, parametric deduplication, stored tampering and audit/outbox rollback. It measures denial-to-audit visibility with a monotonic clock and requires at most five seconds for the executed cases. These external provider protocols remain mocked throughout. `npm run check` includes the unit/contract checks; full smoke and remote acceptance remain distinct evidence. Never claim a mock provider proves real external settlement or signature validity.
