# Policy, Claims & Payments

Code: `backend/policy-claims-payments`. This module owns issuance, policies, premiums, payments, reconciliation, claims, evidence and indemnities. It receives Acquisition offer references; it maintains separate adapters for payments, signatures and other integrations it owns.

Explicitly granted web analysts can list open claims through the [claims inbox](claims-inbox.md). Identity owns the `claims:read` permission; this module owns the list, its ordering and the read audit. A customer reports a claim from the native app through the [claim report](claim-report.md): a draft, one verified upload per declared file and a submission that assigns the single case number and opens the claim in that list. The [case file](claims-inbox.md#case-actions) supports analyst decisions, expert assignments and information requests, and a web policyholder can answer a request.

The [regulator and reinsurer reports](regulatory-reports.md) guide covers the monthly period reports, their custody and the simulated delivery to each destination, behind per-operation operator grants.

The [assistance provider search](assistance-provider-search.md) guide describes the shared lookup rules and the versioned synthetic directory.

The [editable claim drafts](claim-drafts.md) guide covers offline preparation, automatic synchronization, revision conflicts, durable customer choices and their SQL/HTTP boundaries. These drafts do not file claims or replace the upload declaration.

The [parametric payouts](parametric-payouts.md) guide describes the flight-delay and heavy-rainfall indemnities, the simulated provider contract, the customer notice and the recovery of pending payments.

The [policy lifecycle](policy-lifecycle.md) guide covers owner web modification, renewal and cancellation, sealed history, replacement eligibility and the versioned customer notice.

## Implemented state

The Worker owns its `policy` schema, runtime role and Hyperdrive. Its academic financial flow consumes signed accepted-offer events, persists policies and charges, signs and issues them using explicit mock provider adapters. The internal event consumer and the private provider RPC evaluate verified flight-delay and heavy-rainfall occurrences against the immutable coverage and create a single indemnity/payment effect; see [parametric payouts](parametric-payouts.md). Business rules, SQL transactions, authorization, integrity verification and idempotency execute in Solventa; only external data, payment and signature providers are mocked. This does not establish legal issuance, real money movement, PCI compliance, external provider integration or production readiness. Evidence upload and assisted claims remain separate capabilities. Owner lifecycle changes are described in the guide linked above.

## Financial HTTP flow

All routes below enter through the web Worker and require the existing sealed web session, except `GET /api/v1/policies`, which serves the native wallet with a bearer token (see [native policy list](#native-policy-list)). Identity verifies the operation, local session and Origin for each write through one `authorizeFinancialAccessV1` RPC. Partner bearer tokens and native credentials do not authorize these web financial operations. Unknown fields are rejected without echo; errors contain only `error` and `traceId`. Responses include `Cache-Control: no-store`, `X-Trace-Id` and `X-Content-Type-Options: nosniff`. API version retirement headers remain applied by the gateway.

1. Accept an immutable definitive offer in [Acquisition](../acquisition-risk/README.md#definitive-synthetic-offers). Its 202 response means `pending_issuance`, not a confirmed charge or policy.
2. Read `GET /api/v1/policies/by-acceptance/{acceptanceId}/policy` until the owner's signed outbox event has been consumed. A missing, pending or foreign acceptance returns the same opaque 404. Before import, an absent row is an internal pending result and does not create a financial rejection or security-denial alert on each poll. An existing foreign policy still follows the audited denial path. Authentication/authorization always precedes this lookup. The query never creates a policy and returns the full document once available.
3. Read `GET /api/v1/policies/{policyId}` to review/download the returned `document` and its opaque HMAC-SHA256 `documentHash` in web step 5. Return this server-provided fingerprint unchanged; clients never receive the signing key.
4. Web step 6 calls `POST /api/v2/policies/{policyId}/charge` with `{ "documentHash": "<reviewed fingerprint>" }` and a stable `Idempotency-Key`. The owner confirms one mock premium and returns `status: charged` with a synthetic receipt; an uncertain result is retried with the same key. A pending policy is never shown as charged or issued.
5. In web step 7, after reviewing the complete canonical document, explicitly accept it and call `POST /api/v2/policies/{policyId}/signature-challenges` with `{ "documentHash": "<reviewed fingerprint>", "accepted": true }`. Policy requires a charged policy and stores an owner-bound, document-bound challenge for at most five minutes (never beyond offer expiry). The mock returns a six-digit `demoCode` to the web UI; no SMS is sent. Three wrong attempts cancel the challenge. Failed-attempt decision captures retain numeric counts 1, 2 and 3; the SQL adapter normalizes the bounded database integer before application arithmetic. `POST /api/v2/policies/{policyId}/signature-challenges/{challengeId}/cancel` with `{}` cancels an unused challenge.
6. Confirm `POST /api/v2/policies/{policyId}/issue` with JSON `{ "documentHash": "<reviewed fingerprint>", "challengeId": "<challenge UUID>", "code": "<six digits>" }` and an `Idempotency-Key` of 1–128 visible ASCII characters. The JSON limit is 1024 bytes. Policy validates and consumes the challenge in the durable issuance command; wrong, expired, cancelled, foreign or differently bound challenges cannot sign. A replay of the same command may use the consumed challenge. Clients cannot submit the amount, destination, owner, approval or alternative offer terms.

The previous `POST /api/v1/policies/{policyId}/issue` continues accepting only `{ "documentHash": "<reviewed fingerprint>" }` for clients loaded before this rollout. Its original combined mock charge/sign/issue behavior and idempotent replay remain available; it does not accept the v2 challenge fields. New clients use the separate v2 charge and signature endpoints. Both versions use the same owned policy records and authorization, and neither version has a retirement date yet.

Policy reads and issuance responses include an optional `payment` object when a premium intent exists: `status` is the single premium's `pending`, `confirmed`, `declined` or `refunded` state, and `reference` is the synthetic provider receipt (`MOCK-<payment UUID>`), present only for `confirmed` or `refunded`. It is read from the same integrity-checked snapshot as the policy, without another query, and is never stored in the command result, so replays of commands completed before this field existed still match. It carries no amount, payment method or destination: the amount is the policy `premium`.

Issuance derives money and ownership from the stored, integrity-checked acceptance. The signature endpoint accepts only a previously charged policy. Its recovery machinery handles both new charge commands and older combined issuance commands. Unresolved charged premiums are refunded after offer expiry. A failed synthetic signature compensates a confirmed mock charge. An uncertain signature result returns 503 and must be reconciled using the same operation identity. Different payloads under an existing key conflict. The returned policy identifies `synthetic: true` and `providerMode: mock`.

### Native policy list

`GET /api/v1/policies` lists the caller's own **issued** policies for the native wallet. It is the only financial route a native user can use, and it only reads:

- Authentication is `Authorization: Bearer <user access token>`; a cookie is ignored and a missing or malformed header is 401 before any RPC. Policy calls `authorizeFinancialAccessV1` with `{ kind: 'mobile', token, operation: 'policies:read', traceId }` and accepts only a native `user` actor whose operations include `policies:read`; any other actor shape is 503.
- The owner comes from the verified principal. The store query filters by client, subject token and `status = 'issued'`, newest validity first, and `PolicyFinance.listOwn` runs the same integrity checks as the single-policy read (sealed terms, document, premium, signature and time seal) for every row. A failed check is `409 integrity_violation`, never a partial list.
- The answer is `{ policies, hasMore, traceId }` with at most six `PolicySummary` items (`policyId`, `product`, `status`, `premium`, `currency`, `effectiveFrom`, `effectiveUntil`, `coverage`). `coverage` is the sealed offer's `mortgage_life` sum insured, the `flight_delay` flight, threshold and payout, or the `weather_event` station, parameter, unit, threshold and payout. The reviewed document, its hash, offer identifiers, payment and signature evidence are never returned. `hasMore` reports older issued policies beyond the six.
- Pending, charged, refunding and refunded policies belong to the purchase flow and are not listed. Contracts ended by modification, renewal or cancellation are excluded in SQL before the native list limit; the web portal retains their history. There are no deductibles, holder name, document number or contact data in the policy model, so none is returned; the wallet does not invent them.
- No resource denial is recorded: the query is scoped to the caller, so there is no foreign resource to hide.

The [policy OpenAPI](../../../packages/contracts/openapi/v1/policies.yaml) documents `listOwnPolicies`; `tests/financial.test.ts`, `tests/financial-http.test.ts`, `tests/financial-access.test.ts` and the native Pact interaction cover it, and `infra/financial-smoke.mts` covers the SQL ownership and status filter.

### Web policy portal

The signed-in customer reads issued policies from the web through three owner-scoped, read-only routes. They use the sealed web session and one `authorizeFinancialAccessV1` call with `policies:read`; an `Authorization` header, a non-GET method or a malformed identifier is rejected before any business read. Each answer is `no-store` and carries `X-Trace-Id`.

- `GET /api/v1/policies/issued` lists at most six issued policies with the same summaries as the native list. The native route keeps its own bearer contract.
- `GET /api/v1/policies/{policyId}/detail` returns, from one integrity-checked read, the `coverage` of the sealed offer, the `exclusions` and `conditionsVersion` of the product, the available `documents` with their `issuedAt`, and the `payments` of the policy.
- `GET /api/v1/policies/{policyId}/documents/{documentId}` returns the PDF of `signed_policy`, `general_conditions` or `premium_receipt` as an attachment.

Rules that keep the portal honest:

- **Exclusions and general conditions live in the code**, in `src/domain/policy-conditions.ts`, as versions with a `since` date. A policy is joined to the version in force at its signature time and reports it as `conditionsVersion`, so they are not part of the signed document or its hash and need no stored column. A published version is never edited: a change adds a version with a later `since`, and policies issued before it keep their wording. Adding a product that no policy could have had before (the `weather_event` entry of the [parametric payouts](parametric-payouts.md)) changes no earlier wording. The portal lists and details the three coverage kinds: mortgage life, flight delay and heavy rainfall. The wording is academic demonstration text in es-CO, taken from the approved prototype for mortgage life. A policy issued before the first version falls back to it. Proving the exact text each customer signed would still require sealing it into the document.
- **Only an issued policy is a portal policy.** A policy still in the purchase flow, a missing one and one owned by another user all return the same 404. A pending one is not recorded as a security denial, like a missing import in the acceptance read; a foreign one is recorded as for any other policy read.
- **Documents.** The issue date of the signed policy and of the general conditions is the signature time. The receipt is dated by the payment and exists only for a confirmed premium. PDFs are generated on request from the checked record by `src/adapters/inbound/pdf.ts`, a text-only PDF 1.4 writer without dependencies and without dates, so the same document gives the same bytes. Nothing is stored. Characters outside Latin-1 are replaced by `?`.
- **Payments.** The model has one premium charge per policy, so the history has one row: `date` is the last state change of the stored payment, `status` is `paid`, `pending` or `failed` (a refunded premium never belongs to an issued policy and fails the integrity check), and the synthetic receipt `reference` appears only when paid. Indemnity payments are not part of this history.
- The portal reads need no migration: the payment query also selects the existing `updated_at` column.

The [policy OpenAPI](../../../packages/contracts/openapi/v1/policies.yaml) documents `listIssuedPolicies`, `getOwnPolicyDetail` and `downloadOwnPolicyDocument`. `tests/policy-portal.test.ts` covers the detail, documents, payment states, integrity failures and the PDF structure, and `tests/financial-http.test.ts` covers the routes, authorization, identifiers and denial recording. The latency objective of the detail read (p95 ≤ 150 ms, p99 ≤ 300 ms) has a scenario, `infra/load/policies.k6.js`; see [load tests](../../../infra/load/README.md) for what has been measured.

### Decision: charge before issuance

The premium is charged before the policy is signed and issued; a policy never becomes `issued` without a confirmed premium. Alternative considered: issue first and charge afterwards, which would leave an issued, unpaid policy after a declined charge. With the chosen order, the recovery obligation is the opposite case, a confirmed charge whose issuance did not complete, which must end issued or refunded.

Each policy has exactly one premium intent (`financial_payment_intents` is keyed by policy and operation). A declined premium is final for that policy and keeps its history; it never moves the policy out of `pending`. Another purchase attempt starts from a new quote and definitive offer for the same customer data and active consent, which produces a new policy and charge and may produce a different premium. Several premium attempts on the same policy would require an additive schema change and new integrity rules; it is not implemented.

The [v2 policy OpenAPI](../../../packages/contracts/openapi/v2/policies.yaml) documents the separate flow, while [v1 policy OpenAPI](../../../packages/contracts/openapi/v1/policies.yaml) preserves the combined legacy request. Queue payloads follow [financial-event.v1](../../../packages/contracts/schemas/financial-event.v1.json); schema validation alone never authenticates an event. Consumers verify its HMAC, exact fields, environment, product/coverage, timestamps and immutable terms, persist effect/inbox/audit/outbox in their owner transaction, then acknowledge delivery. Delivery is at least once, not a distributed transaction or exactly-once transport. Rejected altered events must not create a financial effect. Parametric events have no public HTTP route.

## Academic rules and document integrity

Local, dev, staging and prod Acquisition may deliver the same signed accepted event through both Queue and the existing private `acceptOfferV1` RPC after its acceptance transaction commits. The background RPC need not wait for outbox claim or Queue acknowledgement. Both reach the same HMAC validation, bounded owner SQL import and inbox contract. Neither delivery authorizes issuance or bypasses the protected document-review/issue flow. Queue remains the recovery transport; concurrent duplicate deliveries must preserve one policy and one local effect graph, and a changed envelope under an existing event ID remains a conflict. See [Acquisition publication](../acquisition-risk/README.md#profiled-synthetic-offers) for background deadlines and configuration.

The following numerical choices are academic implementation rules, not values prescribed by the functional or architecture sources. `academic-financial-1` preserves the flow/integrity rules. Acquisition versions its offer rules separately: a 15-minute offer/signature window, one-year mortgage coverage for the offered outstanding balance, and a separate one-day flight product with a 180-minute threshold and COP `100000.0000` indemnity, once per policy. A flight event does not trigger a mortgage indemnity. The weather coverage's numbers are in [parametric payouts](parametric-payouts.md#variants). Money uses canonical DECIMAL(19,4) strings with four places and exact integer validation, never floating-point arithmetic.

The approved, signed offer revision supplies the premium, currency, coverage and validity. A producer's accepted event cannot be replaced by a provisional quote or a caller-supplied approval flag. Policy verifies the event's exact shape, HMAC and environment before import. An acceptance made after expiry is rejected. Delivery after a valid acceptance does not rewrite its history. A new premium is not started after the signing deadline; a prior confirmed premium is reconciled and refunded if the signature window has expired.

Documents are canonical JSON strings so SQL JSON property ordering cannot change their keyed fingerprints. On each protected use, the store's mutable policy projection must match the sealed terms, coverage and document. An issued policy additionally requires its persisted confirmed premium, valid synthetic signature receipt and keyed issuance timestamp in the append-only signature row. A parametric occurrence before that timestamp is not covered even if the offer's effective period already started; an administrator changing the timestamp without its keyed seal also blocks use. The timestamp records the owner's emission transaction, not an external legal timestamp. A command result cannot override those authoritative fields. The idempotency key is hashed with the actor before storage; raw caller keys are not copied into the financial command table.

The web viewer presents a readable summary and then the complete canonical document. Its download retains the exact JSON bytes used for the fingerprint; the mockup's PDF pages are a visual reference, not a claim that a signed PDF exists. The checkbox is enabled on the complete-document page. The simulated code is shown explicitly so testers can exercise failure, expiry, cancellation and success without a real messaging provider. Challenge creation, failed attempts, cancellation and verification persist decision capture, audit and outbox in their owner transaction without storing or logging the raw code. The `0008_signature_challenges.sql` migration and minimum runtime grants must be applied in each environment before deploying this API; existing policy and signature rows are unchanged.

## Transactions and recovery

Policy/premium states must agree before an operation: pending permits no premium or a pending/declined premium; charged/refunding requires confirmed; refunded requires refunded; issued requires confirmed and the sealed signature. Confirmed/refunded references must match the deterministic mock operation identity. An unknown provider lookup can start a settlement only for a pending intent. A claimed local confirmation without matching provider proof, or an altered confirmation reference, is audited and rejected without a new charge. These checks also preserve an uncertain pending operation's legitimate lookup-based recovery.

Both issuance versions validate a completed command against the current terminal policy. An issued result replays successfully; a matching refunded result returns `signature_failed`, allowing clients to read the confirmed refund without another charge or signature. A mismatched result remains an `integrity_violation`, including after autonomous refund reconciliation.

### Autonomous issuance recovery

A client retry with its existing command identity still recovers immediately. Without one, the Worker's `scheduled` handler runs `PolicyFinance.reconcileIssuances` once per minute in local, dev, staging and the isolated production demo. It selects at most 25 policies whose latest policy or premium activity is older than two minutes, so an in-flight customer request finishes first:

- `charged` and `refunding` policies, which always hold a confirmed premium;
- `pending` policies whose premium intent is still `pending`, because the provider may hold a charge whose confirmation was never recorded. An unresolved intent never ages out of recovery.

Selection runs oldest activity first across both groups and atomically refreshes the selected policy's `updated_at` as recovery activity. It changes no financial state, command, signature or payment. This rotates bounded batches so an unchanged or rejected candidate cannot permanently hide later charges. A worker interrupted after selection leaves the selected records eligible again after the same grace period. Selection needs only the existing Policy runtime grants and no new schema.

Each candidate needs an unfinished customer command (`financial_commands.result IS NULL`) for that policy. Recovery locks the policy with that command and verifies that its request hash authorizes the current document. It then continues through the same transitions as the HTTP path: a confirmed charge is signed and issued before the offer deadline, or refunded after it; a `refunding` intent finishes its refund. A pending intent continues only when the provider lookup already reports `confirmed`. Recovery never starts a new provider charge, so an intent the provider never received stays `pending` without an effect. Issuance completes the customer's original command, so a later client retry with any key reads the same policy. Concurrent recovery and client retries are serialized by the policy lock, the immutable intent and the `charged → issued` guard, and produce one charge and one signature.

Every decision recorded by recovery (`premium.confirmed`, `policy.issued`, `premium.refund_requested`, `premium.refunded`) carries `inputs.trigger: "reconciliation"` in its decision capture, with the same rule version, offer, payment and provider evidence as a customer-triggered decision. The audit actor remains the customer whose command is completed. A refund still ends in the audited `signature_failed` rejection; an integrity failure is audited and the candidate is examined again on the next run until it is reconciled administratively.

Each processed candidate logs `financial_reconciliation` with the environment, its trace UUID and `outcome` (`issued`, `refunded`, `unchanged`, `rejected` with its `error`, or `unavailable`). A `signature_failed` result is followed by an integrity-checked owner read: only a stored `refunded` state produces that outcome; an in-progress refund remains `unchanged`, and an unreadable state is `unavailable`. The trace correlates with the audit and outbox records; no policy, customer or provider identifier is logged. An `unavailable` outcome, such as an uncertain provider refund, is retried by a later eligible run. With no index on policy status, selection scans owned policies, which is acceptable for synthetic volumes but should be revisited before real data.

Business outbox persistence does not deliver a customer notification. A confirmed parametric indemnity stores the `policy.indemnity.notice` event for the notifications story, but nothing delivers it yet. This remains an explicit implementation limit.

The web channel implements those retries and reads the owned policy after a signature failure. The `signature_failed` code can also occur while another request is refunding; only an authoritative `refunded` state confirms compensation. The client preserves the original policy/document command key during recovery and does not claim a completed refund or offer another purchase while the state is `refunding`. A document mismatch requires another document read and explicit review before retrying confirmation. The existing charge/signature contracts remain owned by this module.

The final issuance transaction checks its timestamp strictly before the sealed offer deadline after acquiring the policy lock. Expiry while waiting for that lock atomically records a refund intent instead of a signature or issuance, then refunds outside SQL. Stored issuance timestamps at or beyond that deadline fail integrity checks, even with a matching timestamp seal. Refund orchestration rereads the current confirmed premium under lock and uses that confirmed provider reference rather than the earlier pending payment snapshot.

The additive financial migrations preserve the baseline tables. `financial_contracts`, `financial_payment_intents` and `policy_signatures` are append-only for runtime; `financial_commands` holds actor-scoped request fingerprints/results. The immutable payment intent records the provider idempotency identity, operation, key and HMAC. Mutable payment lookup starts from this reference rather than filtering mutable operation/key fields; tampering cannot hide an earlier payment and create another charge. Its foreign key also prevents changing the referenced payment ID. The HMAC binds the ID/key/operation as well as policy/amount/currency. A unique accepted offer/revision index prevents another policy even if a producer publishes a different acceptance ID. Inbox rows carry payload digests and policy references, so an identifier reused with changed content is a rejection rather than a replay.

No SQL transaction remains open during a provider call. The use case commits a stable payment intent, queries for a previous provider outcome, settles only when eligible and persists acknowledgement. `SqlMockPaymentGateway` keeps the explicitly synthetic provider's operations in `policy.mock_gateway_operations`; recovery therefore works across service instances and process restarts. Its ledger is separate from business state and does not establish distributed atomicity. A confirmed premium survives an emission persistence failure; a retry reconciles it without charging again. Signature failure or expiry first commits the `refunding` intent, which prevents concurrent issuance, then performs the idempotent provider refund. A concurrent operation that already issued wins before the refund intent, so its charge is not reversed. An uncertain acknowledgement/refund returns 503 and is recovered using the existing intent.

A newly inserted mock operation returns its persisted fields from the same statement. A collision still reads the original row and verifies its request hash, operation, amount and currency; it never overwrites an existing operation or refund. Policy SQL adapters await every query and COMMIT/ROLLBACK before returning a business result. In a Worker invocation, only the subsequent client transport close is registered with `waitUntil`, retaining its actual promise. Without an invocation context, or if registration fails, cleanup remains awaited. Connections are created per operation, never shared between requests; this follows the [Hyperdrive connection lifecycle](https://developers.cloudflare.com/hyperdrive/concepts/connection-lifecycle/). No authorization, transaction, provider acknowledgement or integrity check is deferred. The adapter ordering tests use controlled transport collaborators; the financial SQL suite separately verifies actual durable replays, collisions, refunds and transactional effects.

The owner confirms each business result with its audit/outbox, and each local consumer effect with inbox/audit/outbox. This includes `premium.requested` in the very first payment-intent transaction before any provider call, and `premium.declined` together with a rejected provider outcome. An outbox failure rolls back those writes rather than leaving an unaudited pending or declined payment. The SQL adapter combines related writes into data-modifying CTEs: payment/immutable intent, audit/outbox and payment/indemnity/claim confirmation. These reduce database round trips without changing transaction boundaries, grants, constraints or the required records. Payment discovery still rejects a missing intent with an orphan payment and validates every returned intent/payment binding. Provider calls remain outside SQL transactions.

Premium confirmation groups its payment update, charged policy state and required audit/outbox in one compound statement under the existing policy lock. It requires the same immutable premium intent and pending payment; a missing effect fails the transaction. Final issuance groups signature insertion, issued state, audit/outbox and completion of the actor's matching command into one compound statement. It returns the stored signature evidence, and the application checks all four fields before COMMIT; a mismatch or any failed write rolls back the entire final transition. Provider settlement/signature calls still occur between owner transactions, never inside them. Replay and refund transactions keep their existing checks.

Accepted-offer import is one SQL statement executed in the database's implicit atomic transaction. Its snapshot reads the inbox row for the event/consumer and whether a contract already uses the acceptance ID or the offer ID/revision; the chained CTE inserts the policy, contract, inbox row, `offer.accepted` audit and outbox event only when neither exists. It must report exactly one outbox row, and a failure of any insert rolls back all five. An existing event returns its original inbox evidence without writes: a matching digest replays only after the stored policy is locked and passes the full integrity check before acknowledgement; a different digest, a missing inbox policy reference, an invalid outcome or an existing acceptance/revision is an audited `event_conflict` with no write. Concurrent deliveries of the same event, or of rival envelopes for the same offer revision, are serialized by the existing primary keys and unique indexes: the losing statement fails with a uniqueness or serialization error, is retried within the bounded SQL attempts and then reads the committed row as a replay or conflict, never creating a second policy. An existing contract with corrupted terms is reported as a conflict at import time rather than an integrity violation; protected reads of that policy still fail the integrity check.

User policy reads filter both owner identifiers in SQL before decoding payment/signature evidence, so even a malformed foreign record remains an opaque 404. The acceptance lookup selects the owner-filtered record and, in the same statement, whether any contract holds that acceptance ID. No contract is an unaudited `policy_pending`; a contract owned by another client or subject returns no evidence and becomes the audited `not_found` that also records the security denial. Both reach the client as the same 404. The application repeats ownership validation. HTTP reads use one committed statement snapshot containing the contract, premium resolved through its immutable intent (including orphan-payment detection) and signature. They do not acquire a write lock or issue separate BEGIN/COMMIT statements. All integrity checks still apply to that snapshot; it is neither cached nor reused to authorize a write. A subsequent issuance or compensation always rereads under its own policy lock. Reads remain subject to the engine's serializable lock scheduling and the existing query deadline; omitting an explicit write lock is not a guarantee of nonblocking access. SQL smoke holds an uncommitted changed projection while document/discovery reads start, then rolls it back and requires both reads to return the committed, coherent document.

The first issuance transaction reads the locked policy evidence and actor/key command together. A new premium atomically inserts its optional new command, payment, immutable intent and required audit/outbox in one compound statement. Failure of any required insert rolls back the bundle before provider use. Existing-payment and completed-command replays retain their state, payload and integrity checks. Premium confirmation and final issuance retain their separate transactions and stored-evidence checks; external calls remain between transactions.

Rejections retain a fixed cause, generated decision UUID and trace UUID, without submitted bodies, cookies, signatures or personal fields. Required rejection persistence failure returns 503. Financial audit retention is provisionally 90 days; metadata does not implement deletion or protect against an administrator.

## Configuration and verification

`financial_http_duration` records only environment, the validated response correlation UUID, HTTP status, monotonic handler duration and a syntactically valid `cf-placement` diagnostic when provided by the platform. It does not log a URL, policy identifier, actor, cookie, request/response body or document. Correlate those durations with the Queue delivery metrics and client timing to distinguish processing from waiting; logs do not substitute the durable business audit.

Each new financial decision stores the application-generated [historical capture](data.md#financial-decision-history) atomically with its state/audit/outbox. It preserves the safe immutable offer/document context, original payment amount and identity, actual provider observations and covered occurrence rather than a generic resource-only placeholder. Completed replays preserve their original history; older captures are not backfilled. Persisted SQL checks cover the shared schema and exact business evidence, including refund/recovery and changes to live projections.

`FINANCIAL_PROVIDER_MODE=mock` explicitly enables synthetic providers in local, dev, staging and prod. An unsupported environment, any other mode or missing/malformed `FINANCIAL_EVENT_KEY` (exactly 64 lowercase hexadecimal characters) fails closed. Prod is a synthetic demonstration, with its own key, SQL roles, Queue/dead-letter queue and minute recovery trigger. Its events retain `environment: prod`; consumers still reject another environment, invalid HMACs, unconsented access, owner mismatches and altered document bindings. Web authentication continues using the existing production WorkOS configuration. Use synthetic customer data; the returned `synthetic: true` and `providerMode: mock` never establish real payment settlement, external legal signature or insurance coverage. Keep the key in each environment's authorized secret custody; never copy it into clients or examples. Acquisition and Policy use the matching key for that environment, never another environment's credential. Apply the owner's additive financial migration and grants before deploying code that uses its tables, following [migration operations](../../infrastructure/migrations.md). Configuring Queue resources and secrets requires a separate verified environment operation; code and dry-run builds do not provision them.

`npm run test:financial` covers domain boundaries, event authentication, authorization and HTTP contracts. `npm run test:financial:sql` executes actual owner SQL and runtime grants in a temporary synthetic database: fresh migrations/replay, ownership (audited foreign and unaudited unimported acceptance lookups), idempotency/concurrency, import rollback per inserted table, replay integrity revalidation, concurrent redelivery and rival envelopes for one offer revision, document binding, altered events, durable mock provider restart, uncertain confirmation reconciliation, recovery after an emission rollback, autonomous recovery of a stranded charge (issue, unrecorded confirmation, expired refund, idempotent rerun and a race with a client retry), signature failure/expiry refunds, parametric deduplication, the weather variant through the provider RPC with its customer notice and recovery of a pending indemnity, stored tampering and audit/outbox rollback. It measures denial-to-audit visibility with a monotonic clock and requires at most five seconds for the executed cases. These external provider protocols remain mocked throughout. `npm run check` includes the unit/contract checks; full smoke and remote acceptance remain distinct evidence. Never claim a mock provider proves real external settlement or signature validity.
