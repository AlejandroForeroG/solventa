# Editable claim drafts

The native app can save and update a partial claim report while offline. The editable resource contains policy, event type/date, place, notes and references to evidence already verified by Policy. It is distinct from the immutable upload declaration and final submission in [claim reporting](claim-report.md). Saving or confirming this draft does not file a claim, upload a file, accept a contract, grant consent or confirm a financial operation. Continue report rereads the owned confirmed version online and restores event data/notes into the existing report form. Its saved references remain in the editable draft; actual file attachments and explicit review/submission are still required. New binary capture and interrupted uploads retain their existing reporting lifecycle.

## Contract and ownership

The [OpenAPI specification](../../../packages/contracts/openapi/v1/claim-drafts.yaml) defines `GET /api/v1/claim-drafts`, `GET /api/v1/claim-drafts/{draftId}`, `GET /api/v1/claim-drafts/evidence?policyId=…` and `PUT /api/v1/claim-drafts/{draftId}`. All require the native bearer session and Identity's `claims:report` operation. Web cookies and partner credentials do not grant access. Policy checks the issued policy's subject and the draft's client/subject owner on each operation. Unknown or withdrawn resources are opaque; no client-supplied owner, premium, payment, contract state or consent field is accepted.

An action has a stable UUID draft ID and command ID, a base revision and a complete partial-draft content snapshot. Revision zero creates; updates use a revision from server history. Unknown or future bases fail. Fields are restricted to the published schema: 120 Unicode code points for place, 600 for notes and ten distinct evidence references. Event time may be absent; a supplied time must fall within policy coverage and no more than five minutes in the future. References must identify unexpired, verified evidence on the same owned policy. The evidence selector returns up to 50 references; the draft list and account capacity are 20. PUT bodies are limited to 16 KiB at both gateway and Policy.

HTTP 200 confirms a draft revision. HTTP 409 with `status: conflict` contains the base, local and current server versions and the conflicting fields. Other refusals use an error/trace envelope: 400 malformed input, 401 invalid session, 403 missing permission, 404 unavailable resource/policy, 409 invalid base/key reuse/capacity, 422 invalid coverage/evidence and 503 unavailable dependencies. A 409 error envelope is not a resolvable version conflict. Responses are `no-store`. [Synthetic examples](../../../packages/contracts/examples/claim-drafts.json), schema tests and mobile Pact interactions cover the boundary.

## Declared merge policy

`claim-draft.fields.v1` performs a three-way comparison using the immutable base from SQL. The server compares each editable field before writing:

| Data | Automatic result | Manual choice |
|---|---|---|
| Event type/date, place, notes | Keep a one-sided change; identical changes converge; changes to different fields commute | Different concurrent values in the same field |
| Evidence reference set | One-sided change; identical changes; union of concurrent additions if the resulting set has at most ten references | Competing removal/change or an oversized union |
| Policy, owner, authority | Immutable and revalidated | Cannot be selected or overridden |

A conflict writes no content revision. Its command result retains both versions, base revision and field names. The app displays the differing values and lets the owner keep local or server values for the conflicting fields; compatible field edits are preserved. The choice becomes a new, durably queued command tied to that conflict and its observed server revision. Policy validates that link and exact local snapshot. If another writer advanced the draft, it compares again against the new current revision. An old choice is never an unconditional overwrite. A no-op confirmation does not manufacture a data revision.

Migration `0015_claim_drafts.sql` adds current drafts, immutable revision snapshots and the immutable command ledger in the Policy schema. Current content, revision, ledger and audit commit in one transaction. Serialization/uniqueness races receive bounded retries. The ledger binds owner subject, command ID, draft ID and canonical payload hash; same-key/different-body requests fail. Retrying an acknowledged command returns its recorded result after access is revalidated. A conflict and its resolution each carry the actor, correlation, revision references and versioned decision capture. Audit events retain the existing 90-day policy; revision/command history is required to reconstruct and safely retry saved drafts. Runtime has no DELETE grants and cannot update revision or ledger rows. Apply migrations through the [migration procedure](../../infrastructure/migrations.md).

## Mobile custody and delivery

The migration catalog includes the unchanged preceding `0013_claim_report_location.sql` and `0014_assistance_requests.sql` versions so that a fresh environment applies them before `0015_claim_drafts.sql`. This preserves compatibility with subsequent deliveries of their consumers; editable draft APIs do not depend on those consumers. See the [data guide](data.md) for schema and runtime permissions.

The [mobile channel guide](../../channels/mobile/README.md#offline-claim-drafts) describes entry points and native setup. The queue stores the minimum draft fields, confirmed base, command, result, conflict and pending choice. Immutable AES-GCM encrypted files live in the app's private document directory; a small SecureStore key/pointer binds the installation, API environment and both owner coordinates. The encrypted generation and pointer are verified by reading back before the UI acknowledges a save. A failed write preserves the last durable generation. Plaintext storage is never a fallback. Up to 20 entries and 256 KiB of plaintext are supported.

Editing the same unsent draft updates its pending snapshot while retaining the action ID and base. The editor pins the revision associated with the content it opened; a subsequent list refresh cannot rebase that content onto a newer server revision. Saving queues the pinned base so the server can merge or report a conflict. Once transmission may have begun, its ID/body are immutable until reconciled. An explicit pending conflict choice is also immutable before its first transmission; a later edit cannot silently replace that saved decision.

List responses only replace a confirmed entry with a strictly newer revision. A list captured before a command acknowledgement, or an earlier response arriving after a newer list, cannot roll back the confirmed content persisted on the device. Equal revisions retain the existing immutable snapshot and local save metadata.

An open editor pauses refresh and delivery for that owner/draft until save or close; other pending drafts continue. The pump rechecks that pause immediately before its durable sending transition. An already attempted command cannot be opened for editing. This prevents a first creation from being confirmed while its revision-zero editor is still changing. Focus cleanup releases the pause; a process restart loses only this in-memory editing pause and resumes the last durable action.

Each opening requires the device authentication prompt. Backgrounding locks access; sign-out/account replacement uses the authentication coordinator's durable clearing path for both policies and drafts. A discard marker prevents reuse when clearing is incomplete. Encryption keys are removed before ciphertext cleanup; unavailable custody fails closed. A lost file, invalid binding or unauthenticated device never yields a usable draft.

The editor remains mounted but hidden while the system prompt revalidates the session, so opening cannot cancel itself. A verified different owner resets every unsaved field; sign-out or permanent access denial unmounts it. The delivery pump has no owner during revalidation and cannot send until the same verified principal returns. A real background transition still locks custody immediately.

Queue list/sync calls bind the stored owner to Authentication's serialized credential execution. A stale UI callback cannot transmit an old queued payload through a newly authenticated account, even before presentation effects run. The existing foreground/generation checks and server authorization still apply.

While the app is active, network recovery or a verified owner session pumps pending actions automatically; an unlocked workspace also retries recoverable service failures every five seconds. A protected workspace may require the device prompt before sending. Closed/background execution is not guaranteed by the operating system; reopening resumes durable pending work. No action is sent with an unverified or different owner session. Offline opening uses the existing protected policy-owner recovery path. Network availability alone never authorizes delivery.

If a cold offline start left stored credentials unverified because the service was unavailable, pending actions trigger session revalidation on foreground network recovery and the bounded foreground polling interval. Delivery waits for Authentication to confirm the principal. Signed-out, pending-logout, locked and permanently denied sessions do not take that recovery path; there is no registration or permission fallback.

Per-action states are pending, sending, confirmed, conflict and failed with recoverable/unavailable, authentication, permanent refusal or invalid-response detail. Commands survive uncertain responses, timeouts, process death and pending choices. A command with an uncertain outcome is immutable until reconciled or resolved. A validated permanent refusal lets the customer explicitly correct the content as a new command, preserving its original base; malformed or unknown error replies do not grant that transition. Confirmation clears its pending command only after the server reply is validated and saved durably. A failed local acknowledgement commit retries the original command. This prevents duplicate drafts/documents without claiming an offline financial or contractual effect.

## Verification

Run `npm run test:claim-drafts`, `npm run test:claim-drafts:sql` after `npm run infra:up`, `npm run test:pact`, mobile lint/types and `npm run check`. CI runs both behavior and real SQL suites. The SQL suite creates and drops an isolated database, applies the production migrations/grants and exercises duplicate races, conflicting payloads, merge/choice/second concurrency, owner isolation, withdrawn access and audit rollback. It also runs the real mobile queue and API adapter through the Policy HTTP use case and SQL store with a response lost after commit. Native custody and Identity decisions are explicit test doubles in that suite; it does not establish native authentication or storage behavior.

On a native development build with `expo-network`, test airplane mode, durable save, force-close/reopen, device unlock, restored network/owner session, one server effect and the per-action result. Repeat with a service interruption, competing server edit, automatic disjoint merge, manual choice and lost response/restart. Check background lock, account replacement and sign-out clearing. Inspect actual SQL revisions/ledger and retained choice through authorized test instrumentation. Android and iOS storage, prompts and lifecycle need their own native validation; a web export or green unit suite is insufficient.
